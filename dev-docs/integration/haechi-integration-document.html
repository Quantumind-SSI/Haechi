1. Executive Summary

Haechi will be developed as an integrated enterprise secure-communications platform, not as a collection of loosely connected security tools. The engineering strategy is to begin with mature, actively maintained open-source networking, identity, policy, cryptography, observability and deployment components, then add Haechi-owned services where the product requires differentiated behaviour.

The first production objective is a dependable, centrally managed WireGuard-based private network for desktop, mobile and server endpoints. Post-quantum key establishment, privacy-preserving access capabilities, optional censorship-resistant transports, adaptive traffic shaping and the Global Intelligence Mesh are added behind explicit interfaces and release gates. This preserves a working product at every phase and prevents experimental features from weakening the core tunnel.

Engineering position: upstream repositories provide building blocks; they do not by themselves establish that Haechi is anonymous, post-quantum secure, formally verified or suitable for classified use. Those claims require an explicit threat model, integration tests, independent cryptographic review, penetration testing, operational controls and evidence from deployment.

1.1 Product outcome

A fully working Haechi release allows an organisation to enrol users and devices, apply least-privilege access policy, establish secure tunnels, select direct or protected transport modes, rotate keys, monitor service health without collecting traffic content, operate gateways across regions, and update or roll back every component safely.

1.2 What Haechi owns

  • The unified endpoint agent and user experience.
  • The control API, tenant model, device lifecycle and deployment workflows.
  • The privacy-capability issuer and gateway verifier that decouple identity from network sessions.
  • The route orchestrator, gateway scoring and signed policy-distribution system.
  • The traffic-shaping policy engine and safe on-device inference integration.
  • The privacy-preserving Global Intelligence Mesh and its model-governance process.
  • The hardened reference architecture, tests, supply-chain controls and product documentation.

2. Scope and Release Boundaries

2.1 In scope

  • Enterprise-managed encrypted networking for Windows, macOS, Linux, Android and iOS.
  • Multi-tenant SaaS, dedicated single-tenant and restricted-network deployment modes.
  • Organisation administration, device enrolment, policy, gateway and route management.
  • WireGuard-based tunnels with post-quantum pre-shared-key reinforcement.
  • Short-lived, unlinkable connection capabilities after enterprise entitlement verification.
  • Optional transport adapters for networks where ordinary VPN traffic is blocked.
  • Privacy-minimised operational telemetry, threat intelligence and signed adaptive policies.
  • Continuous delivery, security scanning, SBOM generation, signing and rollback.

2.2 Not assumed at project start

  • That changing encrypted packet payloads with a VAE is technically valid. Haechi shapes observable metadata—timing, padding, batching and cover connections—without corrupting authenticated ciphertext.
  • That traffic can be proven “statistically indistinguishable” without a defined adversary, dataset and reproducible evaluation.
  • That post-quantum security can be enabled only after detecting a “quantum signature.” Harvest-now-decrypt-later requires quantum-resistant protection before an attack is observable.
  • That a no-logs claim follows from policy alone. Gateway data flows, correlation paths, support tooling and telemetry must be designed and tested for unlinkability.
  • That Tor, I2P or an obfuscation proxy is suitable for every enterprise environment. These remain opt-in transport profiles with legal, performance and abuse controls.

3. Engineering Principles

  1. Working core first. A secure direct tunnel, identity, policy and operations plane must remain usable independently of experimental features.
  2. Adapters over deep forks. Integrate through stable APIs, libraries and sidecars. Fork an upstream project only when no supported extension point exists.
  3. Cryptography is never improvised. Use standardised algorithms and maintained implementations; require external review for Haechi protocol composition.
  4. Fail closed. Expired policy, invalid signatures, route ambiguity and credential-verification failure must deny access or fall back only to a pre-approved safe mode.
  5. Privacy by data minimisation. Gateways and analytics systems do not receive payloads or durable user identifiers.
  6. Reproducible supply chain. Pin releases or commits, build in controlled CI, produce an SBOM, sign artefacts and verify signatures at deployment.
  7. Evidence before claims. Product language must track measured capabilities, audit results and deployment scope.

6. Haechi-Owned Integration Components

6.1 Endpoint Agent

The endpoint agent is the only component allowed to coordinate tunnel state on a user device. It exposes a stable local API to the UI and hides platform-specific networking behind adapters. Responsibilities include enrolment, device-key custody, capability acquisition, route activation, DNS configuration, kill-switch enforcement, protected-transport selection, signed configuration validation, telemetry minimisation and safe update/rollback.

6.2 Control API

The control API provides tenant-scoped administration for organisations, users, devices, gateways, routes, policies, releases and audit events. It uses Keycloak for administrator identity, OPA for authorisation decisions and PostgreSQL for durable state. Every mutating operation is idempotent and emits a versioned event.

6.3 Privacy Capability Service

This service separates enterprise identity from gateway admission. An authenticated user proves entitlement to an issuer; the endpoint obtains a blinded or otherwise unlinkable, short-lived capability; a gateway verifies the capability locally without calling the identity provider. Capabilities are audience-bound, policy-bound, epoch-limited, replay-resistant and deliberately coarse enough to prevent fingerprinting.

Security gate: this protocol is not production-ready until its privacy properties, issuer/verifier collusion assumptions, revocation design, replay protection and metadata leakage have been independently reviewed. Bulletproofs or any other primitive must not be adopted simply because a repository exists.

6.4 Route Orchestrator

The orchestrator selects eligible gateways from organisation policy, region, service health, jurisdiction rules, capability audience, latency and capacity. It returns a signed route plan rather than directly controlling endpoint traffic. The endpoint validates the plan, applies local policy and reports only a coarse success/failure result.

6.5 Traffic-Shaping Engine

Release 1 uses deterministic, bounded profiles for padding, pacing and batching. Later releases may use an ONNX model to select profile parameters from local network conditions. The model must never rewrite authenticated ciphertext, generate arbitrary third-party traffic, or create unbounded cover traffic. Any cover connection terminates at a Haechi-controlled endpoint and is constrained by bandwidth, cost and abuse policy.

6.6 Global Intelligence Mesh

The GIM converts privacy-reviewed operational observations into gateway scores, transport recommendations and traffic-shaping policy. Collection, model training and policy publication are separate security domains. A model cannot be deployed directly: it must pass an evaluation suite, receive an approval record, be signed, support rollback and declare the client versions with which it is compatible.

9. End-to-End Connection Flow

  1. An organisation administrator federates its identity provider through Keycloak and defines device, route and feature policy.
  2. The user enrols a device. The endpoint creates a hardware-backed device key where the platform supports it and proves possession.
  3. The agent authenticates to the identity plane and requests an access capability for a coarse service class—not a specific browsing destination.
  4. The capability service checks entitlement and issues a short-lived unlinkable token. The identity-plane session ends before gateway connection.
  5. The route orchestrator returns a signed list of eligible gateways and approved transport profiles.
  6. The agent establishes Rosenpass key reinforcement, configures WireGuard, verifies gateway identity and activates the kill switch before protected traffic is accepted.
  7. If direct transport fails and policy allows it, the agent activates an isolated protected-transport adapter and retries without weakening authentication.
  8. The gateway verifies the capability locally, applies service and abuse limits, and forwards encrypted traffic through controlled egress.
  9. The endpoint and gateway emit only allowlisted health events. The telemetry boundary strips prohibited fields before analytics.
  10. The GIM may produce a new signed route or shaping policy. The endpoint validates version, signature, compatibility and local enterprise policy before activation.

10. Deployment Topologies

10.1 Multi-tenant SaaS

Shared regional control-plane services with logical tenant isolation and separate gateway pools where required. Suitable for enterprise pilots and premium managed service. Tenant isolation is continuously tested and sensitive signing keys remain outside application pods.

10.2 Dedicated enterprise or CNI

Single-tenant control and data plane in a customer-approved region or account. Customer-managed keys and identity federation are supported. Operational telemetry can remain inside the customer boundary, with only aggregated health exported under contract.

10.3 Restricted or disconnected environment

No runtime dependency on public SaaS. Releases, trust bundles, revocation epochs and model/policy updates move through a signed offline promotion process. The platform must continue operating safely when external intelligence feeds are unavailable.

12. Verification and Acceptance Criteria

12.1 Functional

  • Administrators can create a tenant, federate identity, enrol/revoke devices and publish least-privilege network policy.
  • Clients can establish, maintain, roam and recover a tunnel across supported operating systems.
  • DNS and traffic do not leave the approved path while the kill switch is enabled.
  • A gateway can validate access without receiving a durable user identity.
  • Gateway and control-plane upgrades support canary, rollback and mixed-version compatibility.

12.2 Performance and reliability

  • Connection establishment p95 at or below 3 seconds under the reference environment.
  • Regional failover and network-roaming recovery p95 at or below 5 seconds.
  • Direct-mode median latency overhead below 10 ms within the reference region; throughput and battery budgets defined per platform.
  • Control-plane target of 99.9% availability for pilot and 99.95% before general availability.
  • Shaping and protected transports publish explicit latency, throughput and bandwidth-cost profiles rather than sharing direct-mode targets.

12.3 Security and privacy

  • No raw traffic payload, full DNS query or durable user identifier appears in the telemetry pipeline.
  • No secret is stored in source control, container image or client log.
  • No unsigned application, container, policy bundle or model reaches production.
  • All critical cryptographic paths have published test vectors, negative tests and independent review.
  • There are no unmitigated critical or high-severity findings at a production release gate.
  • Privacy assertions are tested against issuer/gateway log correlation, timing, replay, revocation and tenant-collusion scenarios.

13. Security, Compliance and Operational Controls

  • Threat model: maintain assets, trust boundaries, adversaries, misuse cases, assumptions and residual risks as version-controlled documentation.
  • Secure development: mandatory review, CODEOWNERS, signed commits/releases, secret scanning, SAST, dependency scanning, fuzzing and protocol interoperability tests.
  • Key management: workload identity, short-lived credentials, hardware-backed or HSM-protected signing keys, documented rotation and break-glass recovery.
  • Data protection: documented lawful basis, regional retention, subject-rights process, deletion validation and a DPIA before user telemetry is enabled.
  • Incident response: severity model, on-call ownership, evidence-preserving logs, customer notification process and compromised-release revocation.
  • Assurance: independent penetration test before production, cryptographic review before privacy/PQ claims, and mapped evidence for NCSC, ISO 27001 and customer requirements.

14. Dependency, Licence and Supply-Chain Policy

  1. Record repository, exact version/commit, source hash, licence, maintainer status and responsible Haechi owner.
  2. Prefer released, supported versions over arbitrary branches. Never build production from an unpinned main or master.
  3. Review copyleft, network-copyleft, trademark, patent and notice obligations before code is linked, modified or redistributed.
  4. Build in isolated CI with locked dependencies; generate SPDX or CycloneDX SBOMs.
  5. Sign binaries, containers, mobile packages, policies and ML models; verify signatures before install or deploy.
  6. Track upstream advisories and end-of-life dates. Every critical dependency has an upgrade owner and replacement plan.
  7. Contribute suitable generic fixes upstream to minimise long-lived private forks.

16. Definition of a Fully Working Haechi Release

Haechi is considered fully working for its declared release scope only when all of the following are true:

  • A new enterprise can be provisioned from infrastructure through identity federation without undocumented manual database changes.
  • Supported endpoints can enrol, connect, roam, fail over, disconnect and uninstall cleanly.
  • Policy is enforced consistently at administration, control, endpoint and gateway boundaries.
  • Identity and gateway session data are separated according to the documented trust model.
  • Cryptographic algorithms, negotiation and key rotation are observable to operators without exposing keys or user activity.
  • Monitoring detects service failure while respecting the telemetry prohibition list.
  • Backup, restore, incident response, key rotation, regional failover and release rollback have been exercised.
  • The shipped SBOM matches deployed artefacts and every artefact verifies against the release trust root.
  • Performance, platform, security, privacy and accessibility acceptance criteria pass in CI or a recorded release test.
  • Marketing and investment claims are traceable to test reports, audits or clearly labelled research objectives.
